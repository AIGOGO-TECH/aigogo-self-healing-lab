# Running this where it matters

This started as a demo for a conference talk and was hardened afterwards,
in that order, which is visible in the git history and is the honest way to
read it. What follows is what was changed, what was deliberately left
alone, and what would still have to be true before this touched a network
anyone depends on.

---

## The one-line summary

The lab is safe to run on a laptop and is structured the way a production
system should be: no secrets in git, least-privilege credentials, an
append-only audit trail, and a change gate that bounds both how often one
device may change and how much of the fleet may change at once. It is not
production-ready, because it terminates no TLS, authenticates no operator,
and has been tested against three routers.

---

## What changed, and why

### Secrets

Nothing is committed. `.env` — generated by `scripts/gen-secrets.sh`,
`chmod 600`, gitignored — is the only place a credential exists. It reaches
the rest of the system three ways:

| Consumer | Mechanism |
|---|---|
| Containers | compose `environment:` |
| Salt master and proxy config | `salt/entrypoint.py` renders `${VAR}` from the environment into `/etc/salt/**` at start, at mode 0600, **outside** the bind mount |
| Salt pillar | Jinja: `{{ salt['environ.get']('NETBOX_API_TOKEN') }}` |
| n8n workflows | `$env.SALT_API_SECRET`, `$env.ES_AUTH_HEADER` — so an exported workflow JSON carries no secret |

`entrypoint.py` refuses to start if a referenced variable is unset. A Salt
master that comes up with an empty device password is worse than one that
does not come up.

### Elasticsearch: one user per component

`xpack.security` is on, and `es/init.py` creates five users from
`es/roles.json`:

| User | May | May not |
|---|---|---|
| `salt_writer` | create and write `napalm-2*`; read and **append** `napalm-audit` | read the remediation history; delete anything |
| `n8n_agent` | read/write the workflow indices; read and append `napalm-audit` | touch the event indices' mappings; delete anything |
| `grafana_reader` | read `napalm-*`, `docker-stats`, `lab-logs`; append `napalm-escalations` | write anything else |
| `stats_writer` | write `docker-stats` | see anything else |
| `log_writer` | append `lab-logs` | read it back |

No role holds `delete` on `napalm-audit`, and `napalm-audit` is a **data
stream**, which rejects update-by-id and delete-by-id outright. Nothing in
this stack can edit or remove its own audit record — including the
component that wrote it.

### The audit trail

A `trace_id` is minted by the beacon that first observes a fault and
carried through the event bus, the Grafana alert, the n8n workflow, the
model's answer, the salt-api call, the state run, and the **commit message
left on the device**:

```
A:srl3# info from state /system configuration checkpoint *
    checkpoint 0 {
        comment "selfheal trace=srl3-20260916T075658Z-36367a actor=n8n/llama3.1 state=restore_interface"
        created "2026-09-16T07:57:22.986Z"
    }
```

Someone with a CLI session on that router and no access to Salt,
Elasticsearch or the ticket system can still see which automated decision
changed it.

The trace lives on the *checkpoint*, not the commit, and that is not an
accident of implementation. An automated change is committed with the
device's revert timer armed, and SR Linux's `commit confirmed` takes no
comment — so the driver writes the message onto the checkpoint it creates
immediately before the change. Which is the better place for it: the
checkpoint is the rollback anchor, so the trace id names exactly the point
you would roll back to. When the audit store and the device disagree, that is a
finding — and without a marker on the device there is nothing to disagree
with.

Beacons track a fault's lifecycle rather than re-reporting it, so one
outage is one trace id with a measured duration, not forty identical
records at twenty-second intervals.

### The change gate

`audit.change_allowed()` runs inside `audited.config`, which every
remediation uses. It is in the state rather than in the workflow because
there are two paths to a device — the n8n/LLM path and the Salt reactor's
drift path — and only one of them ever went through n8n. The drift path had
no rate limit of any kind: a device that drifted and failed to converge was
reconfigured every twenty seconds, indefinitely.

Four ways to refuse:

1. **Maintenance freeze** (`maintenance:enabled`). During planned work "the
   config does not match the source of truth" is the expected state, and an
   automation that reverts an engineer's change mid-window is worse than no
   automation.
2. **Per-device rate limit** — three changes per device per hour. A device
   that keeps drifting back does not need a fourth push.
3. **Blast radius** — at most two *distinct* devices changed in any fifteen
   minutes. This is the one that matters at scale, and it is a different
   control from (2) for a reason: one bad row in the source of truth faults
   every device at once, and each of those remediations is individually
   within its per-device budget. Idempotent, correct by its own lights,
   applied to the whole network in a minute. The third device is where a
   systemic mistake stops and a human starts.
4. **The audit store is unreachable**, so none of the above can be checked.
   Fail closed. An unattended change with no possibility of a record is
   exactly what this is for.

### Idempotence is not correctness

This is worth stating plainly because the deck used to imply otherwise.
A state that reliably drives a device to the same configuration proves that
the configuration matches the template. It proves nothing about whether
that configuration was the right thing to want.

Three things were added because of that:

* **Outcome verification** (`_modules/verify.py`). Every remediation
  declares a check on what it was *for*, separate from the config it
  writes: the interface is operationally **up**, the IS-IS adjacency
  formed, the session reached established. An interface can be
  admin-enabled and still down; both ends of a link can agree on an MTU and
  the adjacency still not form.

* **Changes that declare a check and fail it are not kept.** Those commits
  are made with the device's own revert timer armed and confirmed only if
  the check passes. The two states that converge to a source of truth
  (`sync_from_netbox`, `sync_from_pillar`) declare no check and commit
  directly — see the README for why, and `docs/lessons.md` 68 for the
  audit that found `golden_config` wrongly in that group. A change
  that does not produce its intended outcome is rolled back by the router
  on its own clock — which still works when what failed is Salt, the
  master, or the network path between them. Salt's own `revert_in`
  schedules a *Salt job* to undo the change; this arms the *device*.

* **Correlated fault suppression.** A dead interface takes IS-IS and then
  BGP with it. The system used to treat that as an independent fault, open
  a second trace, and push `restore_bgp_neighbor` to a device whose BGP was
  not the problem — a remediation that then succeeded idempotently and
  achieved nothing. BGP faults are now reported as symptoms while an
  interface fault is open on the same device, and the suppression is itself
  recorded.

### A detector that cannot see must say so

The alert rule ran an entire outage reporting `health: ok, state: inactive`
while every query it made came back `401 Unauthorized`, because
`execErrState` was `OK`. It is now `Error` — and because a rule that cannot
read Elasticsearch has no idea what is wrong with the network,
`policies.yml` routes `DatasourceError` to an escalation store rather than
to the remediation webhook. A broken detector must be loud and must not be
able to start a config push.

### Operations

Volumes for everything stateful, including Grafana, which had none — a
`docker compose down` wiped the entire observability plane, and every
dashboard, datasource, alert rule and contact point had been created by
hand in the UI. All of it is provisioned from `./grafana` now; the volume
holds only what provisioning cannot rebuild (alert state, silences,
annotations).

Proxy minion keypairs are on volumes too. Without that, recreating a proxy
regenerated its keypair, the master rejected it as an impostor for an id it
had already accepted, the proxy exited, and the device silently stopped
being managed. Recovery is `salt-key -d <id>` on the master.

Also: healthchecks with dependency ordering, log rotation on every service
(json-file with no `max-size` fills a disk, and the first symptom is
Elasticsearch refusing writes), memory limits, pinned image tags, ILM
retention, an Elasticsearch snapshot repository, and ports bound to
`127.0.0.1` by default.

## What is deliberately still not production

### No TLS anywhere inside the stack

Every service talks plaintext HTTP on the `clab-selfheal` bridge network.
To fix: enable `xpack.security.http.ssl` on Elasticsearch and set
`ca_certs` / `verify_certs` in `salt/master.d/elasticsearch.conf` (the
returner supports both), turn off `disable_ssl` in
`salt/master.d/api.conf`, and put a reverse proxy in front of Grafana,
Kibana, NetBox and n8n. Until that exists, `BIND_ADDR` stays `127.0.0.1`.

### No operator authentication or authorisation

Grafana has one admin account. NetBox has one superuser. n8n's owner
account is created by hand on first visit — n8n 1.x dropped
`N8N_BASIC_AUTH_*` in favour of user management, and there is no way to
seed that from the environment. In production all four would be behind SSO,
and Salt's `external_auth` would name real operators rather than one shared
secret.

### `$env` is readable from n8n Code nodes

`N8N_BLOCK_ENV_ACCESS_IN_NODE=false` is set, which is the wrong default for
a shared automation server where anyone can author a workflow. It is on
here because the alternative is committing the salt-api secret into the
workflow JSON. The exposure is bounded by what the container is given: the
n8n container has the salt-api secret — already scoped to `state.apply` on
`srl*` — and does not have the Elasticsearch superuser password, the NetBox
token, or the device credentials.

### Elasticsearch audit logging is off

`xpack.security.audit.enabled` needs a Gold licence. Who logged in to
Elasticsearch and what they queried is therefore not recorded. The
application-level audit trail in `napalm-audit` is unaffected.

### Secrets are in a file, not a secret manager

`.env` at mode 0600. There is no rotation, no expiry, no vault, and no
audit of who read it. The device credentials in particular are the same on
every router.

### Scale is untested

Three routers, one Elasticsearch node, one Ollama instance, all on one
laptop. The controls that exist for scale — the blast radius limit above
all — are correct in design and unmeasured in practice. What would have to
be tested before trusting them:

* a **correlated fault storm**: one root cause faulting twenty devices at
  once, to see whether the blast radius limit stops it at two and whether
  the audit trail makes the root cause findable afterwards
* a **wrong source of truth**: NetBox serving bad data, to see how far it
  propagates before something refuses
* **event bus throughput**: beacons at 20s intervals across a real device
  count, and whether the Elasticsearch returner keeps up
* **the model as a bottleneck**: one Ollama instance serving concurrent
  faults serially

### The licences are a product problem, not a lab problem

Verified by reading them out of the images this repo pulls, not from
memory. Three of the components cannot simply be resold, and they are not
the ones people expect:

| Component | Licence | What it stops |
|---|---|---|
| **n8n** | Sustainable Use License | Internal use is fine. **Reselling n8n as part of a product is not.** Not an open-source licence at all. |
| **Elasticsearch** | Elastic License 2.0 | Forbids offering it to third parties as a managed service. |
| **Grafana** | AGPL v3 | Running a *modified* Grafana as a network service obliges you to offer the modified source to its users. |

For a lab this is irrelevant. For anything sold, n8n is the hard one: the
decision layer would have to be replaced. The usual swaps are OpenSearch
for Elasticsearch (Apache-2.0), an unmodified Grafana or a permissive
dashboard, and orchestration written directly against Salt rather than
through a workflow engine.

Worth deciding early. Swapping a component after it is load-bearing costs
far more than choosing differently at the start — and the architecture in
this repo does not depend on n8n specifically. It depends on there being
*something* between the alert and salt-api that can call a model and stop a
bad answer.

### Single node everything

One Elasticsearch, one Salt master, one n8n, one NetBox. Every one of them
is a single point of failure, and the Salt master in particular is a single
point of failure that can reconfigure routers.

---

## If you are adapting this

Change every credential in `.env`, change the device passwords on the
devices, put `BIND_ADDR` behind a proxy that terminates TLS, and read
`docs/lessons.md` before assuming any of this works the way it looks like
it works.
